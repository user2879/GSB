# TxDiag 设计说明

## 1. 执行模型

`txdiag.engine.Engine` 使用中心确定性仲裁器推进轮次。每个被准入事务对应一个提交到 `ThreadPoolExecutor` 的真实工作线程；引擎按轮处理锁请求、版本读写、提交/回滚和死锁，工作线程接收已授予的操作并回传确认令牌。这样同时满足：

- 事务确实运行在工作线程池中；
- 锁队列、死锁牺牲和规范化轨迹不依赖 OS 线程调度；
- 每轮结束前可以等待所有本轮工作线程确认完成。

稳定顺序统一使用 `(start_seq, txid)`。准入、操作执行、等待队列、提交、超时处理、死锁牺牲与 GUI 渲染均使用这一顺序或由它派生的稳定顺序。

## 2. 规范化时间与真实超时

“真实单调时钟超时”和“两条路径逐字节一致的等待时长”在严格字面上相互冲突：真实纳秒耗时不可能逐字节复现。实现采用双通道：

- **决策通道**：等待截止时间由 `time.monotonic_ns()` 计算，真实决定是否超时；总量预算限制超时等待额度。
- **规范化通道**：轮内事件使用固定的逻辑毫秒（默认每轮 10 ms），等待时长由轮次差得到。此通道进入 SQLite 的规范化轮次、重放比较与双路径字节比较。
- **观测通道**：每次等待、配额排队、准入和加锁的真实 monotonic 毫秒保存到 `observed_json` 与快照的观测数据中，用于审计真实等待。

因此，`round.events[].wait_ms` 与轮次摘要是可复现的规范结论；`observed_rounds[].wait_observations[].observed_wait_ms` 是实际耗时。`E_TIMEOUT` 的触发仍完全依赖真实单调时钟，而不是人为 `sleep` 模拟。显式 `hold-lock` 故障注入只用于验证超时路径；正常等待由持锁事务的自然推进产生。

## 3. 隔离级别与版本

版本记录包含行键、版本号、值、创建事务、状态（`uncommitted`/`committed`/`aborted`）、创建轮与提交轮。读取规则：

| 隔离级别 | 读锁 | 可见版本 | 读锁持有 |
|---|---|---|---|
| RU | 不取读锁，允许脏读 | 最新非中止版本（可未提交） | 不适用 |
| RC | S | 最新已提交版本 | 语句结束释放 |
| RR | S | 首次读取版本固定 | 语句结束释放，依靠版本固定 |
| Serializable | S+X | 最新已提交或本事务写入 | 持有到事务结束 |

所有写操作取 X 锁并持有到提交/回滚。行键处于 X 时排斥其他 S/X；S 可共享。Serializable 的每次首次访问显式记录 S 与 X 两个加锁事件。

## 4. 等待、预算与死锁

每个行键维护稳定排序的等待队列。释放锁后从队首尝试授予；某个 X 等待者无法获得时，后续等待者不越队。等待记录从 `wait_start` 到 `wait_end(granted|timeout)`。

每次完成的等待按规范化等待时长消耗全局预算；超时则按完整截止额度计入。预算轨迹只使用规范化逻辑时长，因此可复现。单次等待上限为 `min(wait_timeout_ms, remaining_budget_ms)`。预算为 0 时请求以 0 ms 超时额度记录 `E_TIMEOUT`。

等待图以“等待事务 → 不兼容持锁事务”为边。检测器枚举简单环并规范化起点；牺牲者取环中最大 `(start_seq, txid)`。牺牲事务的所有锁释放、未提交版本标为 `aborted`，随后立即重新服务等待队列。算法只依赖锁状态，不依赖线程调度。

## 5. 按行与区间合并路径

`LockManager` 的行级状态是语义真相。区间路径在每次状态改变后将“相邻且持有者集合与锁模式完全相同的行”合并为区间；冲突检查使用区间内精确行键集合，因此不会因无关中间行产生假冲突。

规范化事件仍然逐行记录 S/X 的获取与释放，所以两条路径产生相同的事件序列、等待时长与摘要。区间合并结果作为路径诊断元数据单独保存于 `range_plan_rounds`，不进入规范化字节。`E_DIVERGE` 使用结构化 JSON 差异定位首个不一致的事务、行键和字段。

默认阈值：`tx>=8 OR rows>=12 OR edges>=10 OR (tx+rows+edges)>=24` 选择区间路径，否则按行路径。

## 6. SQLite 账本与快照

账本主要表：

- `rounds`：轮次号、整数格式版本、规范化轮次 JSON、SHA-256、真实观测 JSON；
- `events`：展开后的稳定事件索引；
- `inflight`：每轮开始前提交的执行中标记；
- `snapshots`：整体快照摘要与状态；
- `recoveries`：恢复审计记录；
- `ledger_meta`：声明摘要、配置摘要、完成状态、未知事务与最后提交轮次。

每轮开始时独立提交 `inflight`，轮结束时在**同一事务**中插入轮次、事件并删除 `inflight`。强制终止后，遗留 `inflight` 中的事务全部标记为 unknown；若终止发生在完整轮次边界，则从最后一个已提交轮次的运行集合减去该轮已提交/中止事务，得到 unknown 集合。

快照包含整数 `format_version`、声明摘要 `declaration_sha256`、内容摘要 `content_sha256`、状态摘要 `state_sha256` 与完整状态。写入使用同目录临时文件和 `os.replace`。打开时比较格式版本、声明摘要、内容摘要和状态摘要；任一不匹配即清除整库轮次后建立新会话，并输出路径排序的稳定差异。绝不会把新旧快照增量拼接。

## 7. 重放

重放从账本读取 `effective_path` 和 `config_json`，拒绝覆盖不兼容会话。引擎重新执行，`ReplayHooks` 在每轮持久化前逐字节比较规范化 JSON；全部轮次通过后，还会比较最终版本表、事务结果、隔离读取结论、死锁牺牲与超时记录。首个不同的轮次事件或最终状态字段会结合上下文报告 txid 与 row，并抛出 `E_REPLAY`。实际 monotonic 观测不参与规范化重放比较，原因见第 2 节。

未完成账本只重放已提交前缀；输出 `INCOMPLETE_REQUIRES_RERUN`、unknown 事务列表和 `exit_report_available=false`，不会伪造强制终止时的退出报告。再次 `run` 会先校验已提交前缀，再继续补齐后续轮次。

## 8. GUI

`txdiag.gui_model` 从引擎结果构建纯数据模型：事务按开始序号、行键按声明顺序、依赖边按端点、事件按 `(round,event_seq)`、配额按轮次排序。Tkinter 只负责渲染该模型，包含：

- 事务—行键访问图与行级依赖边；
- 锁持有与等待关系；
- 每轮等待图、环与死锁牺牲依据；
- 配额占用和排队时间线；
- 各隔离级别读取结论；
- 事件轨迹和账本/快照摘要。

模型构建可在无 Tk 环境测试；当前 Linux 验证容器未安装 `libtk8.6.so`，因此只完成编译和无头模型验证，Windows 交互启动命令见 README。
