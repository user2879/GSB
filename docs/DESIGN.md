# 技术设计与一致性不变量

## 1. 模块边界

| 模块 | 职责 |
| --- | --- |
| `sql_parser.py` | 受限 SQL 词法/语法分析、谓词展平、稳定规范化 |
| `plan.py` | 不可变计划树、摘要、行数估算、编辑变换、逐字节比较与首个差异定位 |
| `spec.py` | 本地 JSON 声明加载与全量强校验、原子规格替换 |
| `ledger.py` | SQLite 账本、WAL、单事务批次、延迟/校验/参数事件、恢复读取 |
| `engine.py` | 快速缓存路径、增量编译、同步/后台全量校验、权威重算、参数版本演进 |
| `snapshots.py` | 快照内容摘要、稳定差异字段、恢复前置校验 |
| `ui.py` | Tkinter 操作界面和后台校验轮询 |
| `cli.py` | 验收演示、三类异常注入、无显示环境入口 |

## 2. 计划模型与稳定摘要

计划节点是冻结数据类：

```text
PlanNode(id, kind, props, children, version, summary, estimated_rows)
```

节点摘要：

```text
SHA256(canonical_json({
  id, kind, props,
  children: [{id, summary}, ...]
}))
```

要点：

- 摘要不包含节点版本和行数估算，两者是独立、可检查的演进字段。
- 计划字节包含版本、摘要、估算、完整属性和子节点；全量一致性要求整个规范化字节串完全相等。
- `AND` 条件在解析后展平并排序；`IN` 值去重排序；空白、大小写、冗余括号不进入摘要。
- 计划摘要使用 SHA-256，规范化 JSON 使用固定键排序、紧凑分隔符和 UTF-8。

## 3. 增量编辑

一次编辑的执行过程：

1. 定位目标节点和祖先路径；目标不存在返回 `E_REF`。
2. 只变换目标节点（下推 Filter 时还会变换其 Scan 子节点并删除 Filter）。
3. 只重建目标节点、被修改节点和祖先闭包；其他子树直接复用同一对象实例。
4. 受影响节点版本 `+1`；未受影响节点摘要与版本逐项校验，并验证实例未替换。
5. 计算受影响集合、直接节点、被删节点和由叶向根的传播依据。
6. 从当前缓存发布整份新视图，旧视图追加为 `STALE`，不作为当前汇总来源。

节点版本在“基础计划 + 全量重放所有编辑”时自然重现，因此增量树与全量树可以逐字节比较，而不是只比较根摘要。

## 4. 全量校验与差异定位

全量路径始终从原始 SQL 新建基础树，再按完整编辑轨迹从序号 1 重放。比较顺序：

1. 根节点 ID、类型、自身属性。
2. 子节点结构与子树。
3. 派生版本、逻辑行数和结构摘要。

这样，如果 Scan 改变导致祖先摘要传播变化，首个不一致节点会定位为 `scan`，而不是根节点；若只有摘要被篡改，则定位到该节点。

后台校验线程使用独立 SQLite 连接。界面线程先得到增量视图，后台完成后再整体替换视图中的校验状态并在账本写入 `verification_records`。

## 5. 快速路径与权威路径

**快速界面查询**

- 只读取 `QueryState.view` 的深拷贝。
- 返回计划摘要、逻辑行数、编译状态、视图摘要和缓存真值标记。
- 不调用 `_compile_full`，不重放编辑。
- 用 `time.monotonic_ns()` 包围缓存读取，超预算返回并记录 `E_LATENCY`。

**权威重算**

- 从当前原始 SQL 生成基础计划。
- 从编辑序号 1 重放完整轨迹。
- 逐字节比较后写 `AUTHORITATIVE` 校验记录和真实延迟记录。

**延迟真值**

每条记录保存 `mono_start_ns`、`mono_end_ns`、`budget_ms`、`elapsed_ms`、业务码和 `truth_source`。界面只展示账本记录；不通过 sleep 人为制造超预算。

## 6. SQLite 账本

整数格式版本同时写入：

- `PRAGMA user_version = 1`
- `meta.ledger_format_version = 1`

主要表：

- `plan_batches`：基础/编辑批次、规范化计划字节、摘要、版本、受影响集合、传播依据、编辑轨迹、延迟、校验状态、游标、陈旧位、内容摘要。
- `edit_attempts`：编译前 `RUNNING` 意图；成功 `COMMITTED`，明确失败 `FAILED`，崩溃遗留 `UNKNOWN`。
- `latency_records`：快速查询、编辑交互、基础/参数重建、全量校验、权威重算的单调时钟实测。
- `verification_records`：同步、后台、权威和重放校验结论及首个差异。
- `parameter_events`：参数版本/分类版本单调事件。

一个成功编辑批次的核心写入在同一事务：

```text
plan_batches + latency_records + edit_attempts(COMMITTED)
             + parameter_events + 旧批次 stale 更新
```

`RUNNING` 意图必须在编译前单独提交，这是崩溃恢复能够区分“已提交”与“未知未提交”的前提。

## 7. 恢复与重放不变量

- 恢复只读取完整提交的 `plan_batches`；`RUNNING` 永远不参与状态推导。
- 启动时把遗留 `RUNNING` 改为 `UNKNOWN`，记录 `requires_rerun = true`，且明确 `exit_report_available = false`。
- 按上下文摘要选择该查询最新 epoch 的已提交批次，从基础树逐批应用编辑。
- 每个批次重放后同时比较计划字节和根摘要；不一致返回 `E_REPLAY`，携带首个编辑序号、批次 ID、节点 ID 和比较依据。
- 批次内容摘要覆盖不可变计划/轨迹字段；读取时重新计算，可先于重放发现存储篡改。

## 8. 快照与整体替换

快照包含：

- 表结构、SQL 集合、编辑轨迹、缩放口径版本；
- 当前参数版本、epoch、各表/SQL/缩放摘要；
- 当前活动查询逻辑计划摘要；
- 各查询计划摘要、参数版本、编辑序号和账本游标；
- 全文档 `content_digest`。

恢复流程：

1. 重算文档内容摘要。
2. 将版本、摘要、计划摘要和游标逐项与当前状态比较，差异按字段字节序稳定排序。
3. 任一差异：不把快照节点合并进当前树；从当前已提交账本重建整份视图并返回 `E_SNAPSHOT`。
4. 全部一致：按快照游标重放账本，逐批比较计划字节。
5. 重放成功：构造函数创建全新 `QueryState`/视图整体替换，返回重放报告。

## 9. 业务错误码

| 错误码 | 场景 |
| --- | --- |
| `E_SPEC` | 规格结构、唯一性、类型、空值位图、查询引用、编辑目标/操作非法 |
| `E_SYNTAX` | SQL 词法或语法错误，附字符位置 |
| `E_REF` | 运行期编辑目标/聚合输出/列引用不存在 |
| `E_DIVERGE` | 增量结果与全量结果不一致，附首个源头节点 |
| `E_LATENCY` | 真实单调时钟耗时超过声明预算 |
| `E_SNAPSHOT` | 快照格式、版本、摘要不一致，附稳定差异列表 |
| `E_REPLAY` | 账本重放/计划字节不一致，附首个编辑序号与节点 |
| `E_LEDGER` | SQLite 格式版本或持久化失败 |

## 10. 验证映射

`tests/` 中的测试直接覆盖：

- SQL 空白/大小写/括号/AND/IN 归一化与语义差异摘要。
- JSON 强校验、首个违规路径、整体拒绝。
- 增量与全量逐字节一致、未影响子树实例/摘要/版本保持。
- 后台全量校验、参数版本陈旧替换。
- 快速路径禁止调用全量编译器、真实超预算 `E_LATENCY`。
- 权威重算 MATCH 与故意分歧 `E_DIVERGE`。
- 未提交意图恢复为 UNKNOWN、账本篡改 `E_REPLAY`。
- 快照成功恢复、内容摘要/版本不符 `E_SNAPSHOT` 与整体替换。
- 三类 CLI 异常注入及 JSONL 日志字段。
