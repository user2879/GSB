# 检索/问答诊断数据定点裁决组件：设计与验证说明

## 1. 范围与目录

本实现完全本地、确定性运行，不访问网络或外部数据集。

- `rdiq/`：可导入包，含校验、定点运算、证据裁决、误差归因、调度、失效传播与账本。
- `samples/base/`：固定整数种子 `20261126` 生成的基线 JSON 规格。
- `samples/edit/`：规则、权重、通道权重、定点口径四类编辑变体。
- `data/`：基线结论、编辑重算结论、崩溃与恢复输出。
- `ledger/`：SQLite 账本与只读备份（备份权限 `0444`）。
- `tests/`：8 组 `unittest` 用例，含 NumPy 独立整数重算交叉校验。
- `tools/verify_byte_identity.py` 与 `run_verification.sh`：一键复核入口。

## 2. 数据与强校验（需求 1）

六类 JSON：`vocabulary.json`、`rules.json`、`weights.json`、`precision.json`、
`fragments.json`、`sessions.json`。每个文档携带 SHA-256 `digest`，加载时先验摘要，
再按固定顺序校验：

- 片段标识、会话标识全局唯一；轮次序号为非负整数且会话内唯一。
- 片段词项与查询词项必须属于受控词表。
- 片段话题标签、轮次规则版本引用、位宽版本引用必须存在。
- 位宽仅支持 `8/16/32`，缩放因子仅支持 `256/1024/4096`。
- 召回通道必须注册，且每个注册通道都有非负整数原始权重。

首个非法条目以 `E_SPEC` 抛出，携带 `entry`（文档名或稳定标识）与 `field`
（字段路径，列表以点号拼接）。

## 3. 定点整数运算契约（需求 3）

置信度始终处于有符号二补码定点域，1 ULP = `1/scale`。

- 权重量化：`q = truncate_toward_zero(raw * scale / 10000)`，再按 W 位有符号范围饱和；
  截断残差记录在每步 `weight_steps`。
- 乘法：两个 W 位操作数进入有符号 2W 位累加器，结果按 2W 位范围饱和。
- 求和：同一 2W 位累加器逐元素饱和相加，`sum_saturated` 显式标注是否溢出。
- 均值/除法：一律向零截断，残差记录为 `mean_residual` / `view_residual`。
- 最终均值按 W 位有符号范围饱和，`confidence_saturated` 显式标注。

证据按话题内 `(topic, channel, terms)` 的内容摘要去重；同组保留命中数最高、
再按通道、片段标识排序的稳定代表，被去重项进入 `deduped` 并记录代表与原因。

## 4. 引用图、确定性与会话视图（需求 2）

图节点层级为 `source -> evidence -> round -> session`。构建时校验引用完整，
并以白/灰/黑 DFS 在排序节点上检测环，环或缺失引用抛出 `E_GRAPH`。

所有集合在序列化前显式排序；JSON 以 `sort_keys=True`、无空白、UTF-8 规范化，
结论不含主机名、时间戳或线程顺序。单调时钟仅出现在独立的
`*.schedule-audit.json` 审计文件，不进入结论摘要。因此重复运行、打乱片段加载顺序、
改变字典遍历顺序都得到相同 `graph_digest`、`round_digest` 与视图 `canonical` 字节。

## 5. 分级误差界与决胜（需求 4）

误差界以保守整数 ULP 表达：

- 来源级：每条采纳证据有通道、话题、相关性三次量化，单证据界固定 3 ULP。
- 证据级：采纳证据来源界之和，加轮次均值截断 1 ULP。
- 轮次级：证据级界再追加 1 ULP；会话视图另计视图均值截断 1 ULP。

三级贡献分别输出 ULP 界、基点占比、主导级与显式 50% 阈值判定。候选证据链前两名
的量化权重差若不超过轮次总误差界，则按“量化权重 -> 通道 -> 片段标识”稳定决胜，
并将 `error_affected` 标为真。

## 6. 失效传播与子集重算（需求 5）

版本/内容摘要变化先映射到来源片段，再沿引用图边传播到证据、轮次与会话：

- 规则或定点口径变化：保守失效全部来源。
- 通道集合变化：仅失效新增/移除通道上的来源。
- 权重变化：仅失效原始权重实际变化的通道或话题上的来源。

输出按会话标识、轮次序稳定排序，并记录每步传播依据。账本发生整体替换时，
新快照先建立全量确定性基线，再只对失效子集重跑；未失效轮次的裁决摘要与证据链
摘要逐项比对，必须保持逐字节一致。`samples/edit/channel-weight` 在本地样本上
演示为 24 轮中仅 22 轮失效。

## 7. 双重配额真实线程调度（需求 6）

`Scheduler` 使用一个分发线程与 `global_limit` 个真实工作线程。分发器维护 FIFO
待运行队列、全局运行数和每会话运行数，仅在两个配额都满足时放行；工作线程在
`Condition` 上阻塞等待，没有任何 `sleep` 或人工延迟。等待开始/结束、运行起止以
`time.monotonic_ns()` 转毫秒记录，测试断言全局峰值不超过上限、每会话峰值不超过配额。

## 8. 账本、整体替换与崩溃恢复（需求 7、8）

SQLite 表包含 `meta`、`batches`、`round_records`、`cursors`。每批次的裁决、
误差归因和游标在同一 `BEGIN IMMEDIATE ... COMMIT` 事务写入，并携带整数
`format_version` 与批次内容摘要。

重新打开账本时，规则版本、权重版本、定点版本或内容摘要任一不一致即整体替换：
先把旧库及其 WAL/SHM 复制为 `0444` 只读备份，再删除旧库重建，并返回差异列表。

强制终止发生在提交前时，SQLite 自动回滚未提交事务；恢复只承认完整批次，
未提交轮次标记为 `unknown_rerun_required` 并重跑，不生成所谓退出报告。恢复后对
已提交轮次按账本记录的规格重算，逐字段比较置信度、证据链摘要与误差归因，
首个不一致以 `E_REPLAY` 定位到会话、轮次与字段。

## 9. 验证命令

```bash
python3 -m unittest discover -s tests -v
bash run_verification.sh
```

实际验证结果记录在 `data/verification-results.md`。
