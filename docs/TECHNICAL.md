# 技术设计

## 1. 组件边界

`replica_repair` 是一个单机确定性实现，但有明确的节点、协调端和账本边界：

- 清单模型/存储：`model.py`、`manifest_store.py`、`manifest_repo.py`
- 节点持久化与 JSONL 协议：`node_service.py`
- 摘要采集与真值判定：`truth.py`
- 预算调度与修复执行：`planner.py`
- SQLite 快照账本：`ledger.py`
- 重放与首差异：`replay.py`
- 端到端编排：`engine.py`
- 确定性样本/CLI：`sample.py`、`cli.py`

没有后台服务发现、外部认证或真实集群依赖。协调端在一次运行中连接所有节点；节点可以独立进程启动、强制终止并重启。

## 2. 清单与记录级升级

### 2.1 规范化

解码时对节点和块显式排序；编码使用规范 JSON（键排序、UTF-8、固定缩进和结尾换行）。语义数组的排序不依赖输入顺序或 Python 字典遍历。

### 2.2 严格校验

所有格式异常统一为 `E_FORMAT`。字段路径使用 JSON 路径风格，例如 `$.nodes[1].blocks[0].size_bytes`。校验顺序为：

1. 对象/数组类型、未知字段；
2. 必需字段；
3. 版本对应字段集合；
4. 标识格式、唯一性；
5. 正整数大小、优先级、权重；
6. SHA-256 摘要格式；
7. v3 派生关系：来源存在、无自引用、无环、来源标识升序、摘要复算一致。

### 2.3 检查点提交协议

旧清单先复制为只读备份。检查点保存：

- 源文件 SHA-256；
- 源版本、目标版本、新 `manifest_version`；
- 稳定节点顺序；
- 已提交节点前缀；
- 每个已提交节点的完整 v3 记录；
- 阶段 `upgrading|complete` 和完成后目标文件 SHA-256。

单条记录的提交顺序为“完成内存升级 → 原子写检查点 → 调用可选审计钩子”。目标清单在所有记录提交后一次性原子替换。若在最终替换与检查点完成标记之间中断，重启会按检查点记录重建相同 v3 文件并补写 `complete`，不会重新读取已提交节点。

## 3. 节点协议与持久化

### 3.1 协议

请求和响应均为单行 JSON，字符编码 UTF-8。单行上限 32 MiB。服务端逐行处理，可保持连接或每次新建连接。协调端每次操作新建短连接，避免多线程共享协议状态。

`get_digest` 返回清单摘要、实际摘要、实际字数和清单字数。`get_block` 额外返回 base64 字节。`put_block` 在目标节点本地校验长度和摘要，写临时文件、`fsync`、`os.replace`，再读回校验。

### 3.2 完整性策略

正常真值链路使用 `strict_manifest=True`：

1. 节点文件长度与清单 `size_bytes` 不一致：`E_BLOCK`；
2. 摘要查询与数据拉取的摘要不一致：`E_INTEGRITY`；
3. 实际内容摘要与节点清单摘要不一致：`E_INTEGRITY`；
4. 以上失败副本不会进入多数投票。

重放使用非严格采集，只记录清单失配，以便把差异定位到账本字段；截断仍无法完成读取，按 `E_BLOCK` 报告。

## 4. 真值规则

每个块的所有有效副本按实际摘要分组。候选键：

```text
(-count, -sum(priority), sorted(node_ids), digest)
```

第一项为频次降序，第二项为优先级权重和降序，第三项为节点标识向量升序，第四项为摘要字符串升序。选择排序第一的摘要，来源节点为支持该摘要的全部节点。失配副本是其他有效摘要；其实际摘要写入 `deviation_digest`。

报告对象不包含运行时间、随机 ID、进程信息或端口，因此相同清单和块字节的 `to_dict()` 可以逐字节比较；测试会对不同输入顺序和重复运行进行比较。

## 5. 调度模型

预算语义：

```text
每轮任务数 <= max_parallel
每轮每个目标节点的 repair_kb 之和 <= per_node_kb
每个任务 repair_kb <= per_node_kb
```

配额按轮重置；跨轮总修复量可以大于单轮配额。任务若在本轮无法装入，记录 `per_node_quota` 或 `max_parallel` 原因并在后续轮重试。若一轮没有任何任务可调度，说明预算无法推进，返回 `E_BUDGET`。

执行器用线程池并发执行单轮任务。为保持账本顺序确定性，本轮全部结果按 `task_id` 提交进度；强制终止钩子只能发生在一笔进度提交之后，因此磁盘上可能多完成同轮其他任务，重启对账会识别“字节已经等于上轮记录真值”的副本并恢复清单摘要，随后账本仍把所有未提交任务标为 `unknown`。

## 6. 账本状态机

### 6.1 快照

- `before`：修复前分布、真值、失配和计划；进度游标随任务提交推进。
- `after`：修复后分布、真值、已完成任务副本、成本；引用 `before` 作为 baseline。
- 只有 `is_active=1 AND is_stale=0` 的快照进入 `current`。

### 6.2 重新打开

`open_for_state(manifest, state_digest)` 检查：

1. `meta.format_version` 与 `PRAGMA user_version`；
2. 当前状态摘要是否等于账本元数据；
3. 当前 active 快照状态摘要是否一致；
4. 进度是否处于 `running|recovering|failed`。

任一不一致会开启新 generation：旧 active 快照全部置陈旧，未完成任务置 `unknown`，当前视图置空，并写入稳定排序的 `stale_impacts`。下一次成功运行创建全新的前后快照，不增量合并旧结论。

### 6.3 陈旧影响

`compute_manifest_diff` 比较节点优先级、块增减、大小、摘要、修复权重、修复来源和派生关系。优先级变化影响该节点全部块；派生关系变化影响目标块和来源块；仅 `manifest_version` 变化且无语义字段变化时影响全部块。原因和列表均排序。

## 7. 重放顺序

重放比较顺序固定：

1. active 快照副本分布（块、节点、`size_bytes`、`digest`、期望字段、优先级、状态）；
2. active 真值（块、摘要、来源集合、候选排序）；
3. 当前磁盘状态摘要；
4. baseline 真值重算；
5. baseline 修复计划重算（任务结构字段）。

首个不一致立即终止并抛出 `E_REPLAY`。差异对象始终给出块标识、节点标识、字段、账本值、重算值和依据。

## 8. 确定性边界

- 块内容样本由 `sha256("group|block|variant")` 重复截断得到；
- 清单和输出 JSON 键排序、列表显式排序；
- 不使用文件 mtime、UUID、当前时间或随机数参与业务判断；
- 节点端口属于运行时信息，不进入真值/计划报告；demo 汇总会记录端口但对确定性比较时排除；
- SQLite 自增快照 ID 只在同一账本生命周期内稳定；demo 每次重建账本，因此重复 demo 的编号也稳定。
